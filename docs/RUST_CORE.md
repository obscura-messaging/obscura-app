# One Rust core for both kits

`core/` holds `obscura-core`, a Rust crate over libsignal and SQLCipher, with Kotlin and Swift
bindings generated by UniFFI. Today it is a spike: nothing in the app uses it. This document
records why the kits should converge on it, what the spike proved, and the plan.

## Why

The Kotlin and Swift kits implement the same protocol twice: Signal sessions and prekeys, the
content store (merge, expiry, outbox), linking and transport, each on its own storage stack, with
its own fake server and its own test suite. [`KIT_API.md`](KIT_API.md) is the authority only
because neither kit's code can be. Every protocol change is written twice (PQXDH/Kyber was), and
the kits drift where no conformance vector reaches.

Signal splits the other way. Its apps duplicate UI and storage per platform, with a team each,
and keep everything that must behave identically in one Rust library, libsignal, which keeps
growing (zkgroup, backups, networking). Obscura already shares its UI through React Native; the
duplicated layer is the kit, which is exactly the layer Signal refuses to duplicate.

### Why not Kotlin Multiplatform

KMP would reuse the Kotlin kit, but libsignal ships no Kotlin/Native binding. iOS would need
either a binding to libsignal's internal C FFI, which is unversioned and changes every release,
or a crypto interface implemented in Swift and called back from Kotlin, with libsignal's
synchronous store callbacks crossing Rust → Swift → Kotlin → SQLDelight. A Rust core calls
libsignal's Rust crates directly, so that problem does not exist.

## What the spike proved

Branch `spike/rust-core`, November 2026. Every criterion set beforehand passed.

| Question | Answer |
|---|---|
| Does libsignal 0.106.2 build for every target, unpatched? | Yes: Linux host, Android `arm64-v8a`/`x86_64` (cargo-ndk, NDK 27), iOS device and simulator. Stable Rust; no toolchain pin. |
| Encrypted storage with a host-supplied key? | Yes: SQLCipher, keyed with 32 bytes from Keystore/Keychain. A wrong key fails; the file has no plaintext header. On Apple, OpenSSL or CommonCrypto both work. |
| Do callbacks and async cross the FFI? | Yes on both: a foreign logger, Kotlin `suspend`, Swift `async`. See "async" below. |
| Can it talk to today's clients? | Yes, both ways: the core decrypts PQXDH prekey messages from `libsignal-client`, and `libsignal-client` decrypts the core's (`core/tests/fixtures/`). |
| Does it package into the apps? | Android: debug and R8-minified release APKs (opt-in, `-PobscuraRustCore=debug`). iOS: the app links it next to libsignal's FFI with no duplicate symbols. |
| Cost? | See below. |

Measured on the spike, untuned (no size-oriented release profile yet):

- **Android:** `libobscura_core.so` is 7.5 MB per ABI stripped (3.6 MB compressed), +7.8 MB
  to the arm64 APK. The app already ships `libsignal_jni.so` and `libsqlcipher.so` (11.6 MB for
  arm64), which the core replaces, so a migrated app gets smaller. Clean build about a minute per
  ABI, incremental about a second.
- **iOS:** a cold XCFramework build on CI takes 5.7 min with CommonCrypto, 11 min with vendored
  OpenSSL; with a warm cache, 49 s and 93 s. A third of the cold time is generating bindings,
  which also builds the whole library for the macOS host; a separate bindgen crate removes that.

## What the spike also taught us

- **Async runs on a thread.** libsignal's store futures are not `Send`, and UniFFI's async
  exports require `Send`. The core should run every operation on one long-lived worker thread
  with a queue, which also serialises operations, and expose async functions over it.
- **Replace, never coexist.** Shipped next to a kit, the core is pure size cost. On iOS it is
  worse: GRDB's SQLCipher and the core's are both in the binary, and the core's `sqlite3_*`
  calls most likely bind to GRDB's copy, silently. Each platform should switch whole, wiping
  local data, which is acceptable before a public release.
- **Kyber prekeys:** the kits delete a one-time Kyber prekey after use and keep last-resort ones,
  rejecting a reused one as a replay. The core now does the same.
- **Identity trust:** the spike trusts on first use per name and device. The kits key identity
  by user through the device directory and, on a change, drop that user's sessions and devices.
  The core needs that directory before it can replace the kits.
- **UniFFI details:** a variant field named `message` breaks the generated Kotlin, so `CoreError`
  is a flat error. Bindings are generated from an unstripped library. JNA needs R8 keep rules
  (`android/app/proguard-rules.pro`). libsignal needs `protoc` at build time.

## Open decisions

1. **SQLCipher crypto on iOS.** Recommended: CommonCrypto. It builds twice as fast, the library
   is 10 MB smaller, and it is what GRDB uses today. The cost is a different crypto library under
   the same SQLCipher file format on each platform. Android has no CommonCrypto and keeps
   vendored OpenSSL.
2. **How iOS consumes the XCFramework.** Recommended: a checksummed release artifact, as libsignal
   is consumed today ([swift/Package.swift](../swift/Package.swift)), so iOS work without core
   changes needs no Rust toolchain.

## Plan

1. Grow the core behind each kit's existing `ObscuraClient` surface, so the bridges and the
   JavaScript do not change. In order: the wire codec (`wire.json` and `link.json` become core
   tests); the content store, where drift costs most; sessions, prekeys and the device
   directory; linking. Transport stays per platform for now.
2. Switch Android to the core, deleting its kit's crypto and storage, then iOS.
3. `KIT_API.md` stops being a contract between two kits and documents the core.

## Running it

`just core-check` (fmt, clippy, Rust tests), `just core-jvm-test` (Kotlin bindings on the JVM),
`just core-android` and `just core-xcframework` (packaging). CI's `Core` workflow runs the first
two on Linux and the Swift tests on an iOS simulator for pull requests that touch `core/`.
